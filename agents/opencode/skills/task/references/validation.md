# Task File Invariants

Enforced by `scripts/ValidateTask.fsx`. Run `dotnet fsi "C:/Users/andre/.config/opencode/skills/task/scripts/ValidateTask.fsx" <path-to-TASK.md>`; pass `--fix` to auto-repair the fixable ones. Exit 0 = clean; 1 = violations; 2 = bad invocation.

1. **H1 matches folder** — `# <TASK-ID> - Title` (hyphen or em-dash separator), where `<TASK-ID>` equals the `.tasks/<TASK-ID>/` folder name.
2. **No redundant title section** — `## Title` is forbidden; the H1 is the task title.
3. **Status header present and well-formed** — `**Progress: X/N subtasks complete** | **Status: <status>** | **Created: YYYY-MM-DD**`, with optional `| **Completed: YYYY-MM-DD**`. Status must be one of `In Progress`, `Blocked`, `Paused`, `Complete`.
4. **Completion consistency** — `Status: Complete` requires a `Completed:` date and a dated `## Decisions` row containing `complete status confirmed`. Progress must be complete unless a dated row contains `complete status waiver` with a rationale; confirmation and waiver may be separate rows. A `Completed:` date without `Status: Complete` is a violation.
5. **Progress counter accuracy** — declared `X/N` must match actual checkbox state inside the lifecycle region from `## Subtasks` through `## Closing Steps`. `N` counts lifecycle `###` headings; a heading counts complete only when all its checkboxes are ticked. Auto-fixed.
6. **Blocked notation** — every `- [ ] [blocked]` item must carry a `- reason` (hyphen or em-dash).
7. **Decisions table dates** — every data row's `Date` cell must be `YYYY-MM-DD`.
8. **Target repos listed** — `## Context` must list at least one `` `./repo-name` `` entry.
9. **Branch naming** — when a repo entry carries a concrete `(branch: ...)` annotation (not `TBD`), the branch name must start with the task ID (`{TASK-ID}-description`).
10. **Stable subtask numbering** — subtask IDs must be strictly ascending in document order and fit the supported integer range. Gaps are allowed after removal; never reuse or reorder an ID. Decimal subsections ascend within their parent. Letter suffixes are forbidden. Closing steps ascend and come after numbered subtasks; C0 may be omitted for non-code tasks, C1 is required, and C2 is conditional on commit/review-artifact scope.
11. **Summary evidence** — every checked checklist item requires a directly associated, non-empty nested `  - Summary:` bullet. Bare indented `Summary:` continuation lines are auto-fixed.
12. **Task path and creation** — task IDs match `[A-Za-z]+-\d+`; creation must target exactly `.tasks/<TASK-ID>/TASK.md`, reject reparse-point traversal, and never overwrite an existing task.
13. **Task kind** — `## Context` contains exactly one `- Task kind: code` or `- Task kind: non-code` marker. Code tasks require C0 and the canonical implementation, build, and tester gates; non-code tasks must not retain those code-only gates.
14. **Adaptive implementation plan** — code tasks contain exactly one `- Implementation plan: TBD`, `- Implementation plan: non-complex`, or `- Implementation plan: complex` marker in `## Context`; non-code tasks contain none. Code tasks require the exact `### 3. Design gate` subtask with the canonical architect-verdict, conditional-gates, and final implementation-plan/structure-approval checkbox text, allowing surrounding whitespace only; non-code tasks are exempt. That gate completes only when those exact canonical checkboxes are checked and every checkbox in the subtask is checked. Until then, no checkbox in a numbered subtask rooted at 5 or later may be checked (draft headings and unchecked placeholders remain valid; closing steps are excluded). After the gate completes, `TBD`, missing, duplicate, or invalid markers are violations. A non-complex plan retains `### 5. Implement and validate`, removes its exact generic HTML placeholder, and keeps the canonical implementation, build, and tester gates in subtask 5. A complex plan removes that generic heading and placeholder, starts task-specific numbered work at `### 5. Implement: ...`, includes at least one top-level integer `Validate: ...` subtask without requiring it to be adjacent, and keeps implementation/build gates in every `Implement:` subtask and the tester gate in every `Validate:` subtask; Discovery occurs once in C0 after build and test evidence, an explicit not-applicable rationale, or a recorded waiver. Decimal `Implement:` or `Validate:` headings are invalid. Heading ranges exclude fenced examples.
15. **Review evidence** — before a review state beyond `NEW`, each build/test evidence field is exactly `Passed: <non-placeholder command/result>`, `Not applicable: <non-placeholder reason>`, or `Waived: <reference>` linked to a dated waiver in `## Decisions`. Arbitrary text, empty/placeholder values, and failed or pending `Passed:` results are violations.
